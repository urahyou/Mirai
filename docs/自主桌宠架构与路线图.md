# 小未来：自主桌宠架构与路线图

> 本文件描述「小未来」从「被动对话桌宠」演进为「有内部状态、能感知环境、会自己行动的自主 agent 桌宠」的早期目标架构与分阶段路线。完整的生活模拟、多角色、分层记忆、隐私和 Agent 权限设计，以 [自主陪伴系统总体设计方案](自主陪伴系统总体设计方案.md) 为准；后续实施应遵循新方案。

## 1. 产品愿景（用户原话归纳）

小未来将逐步具备：

- **行动**：主动会话、agent 执行、屏幕观测
- **关系**：多角色人物互动、群聊
- **成长**：养成系统、好感系统
- **状态**：实时感知电脑状态与时间、情绪系统（情绪影响决策/行动/会话）
- **信息**：自动获取资讯、记录日程、会议提醒
- **记录**：监听录音整理记录每天生活、自己写日记

## 2. 已拍板的技术决策（决策记录，勿随意推翻）

| # | 决策 | 说明 |
|---|---|---|
| D1 | 记忆**不引重框架**（Mem0/Zep/Letta 等），Graphiti 只作为高级实验适配器 | 发布版采用本地分层记忆、普通关系表和可选向量检索；详见新方案 |
| D2 | 设置与轻量状态使用 JSON；生活事件、日记和关系记忆使用单文件数据库 | 旧 JSON 抽象仍保留；多角色和日志型数据不能继续散落在独立 JSON 文件中 |
| D3 | **tool-calling / agent 执行：嵌入 pi SDK**，不自行实现 function-calling | pi 提供进程内 `createAgentSession`/`ModelRuntime`，自带工具循环、子 agent、自定义工具与白名单；小未来**不把大脑交给 pi**，而把 pi 作为「执行/推理引擎」按需唤起 |
| D4 | 双大脑分层：**本地大脑 + pi 引擎** | 本地 LLM（性格/情绪/轻对话/状态机）+ pi 云端 LLM（复杂推理/工具编排）。**只分离职责，分权受限**（见坑 1） |
| D5 | 录音**默认自动检测、可关** | 事件驱动录制（检测到有意义片段才录），不是无脑全录；感知开关统一收敛于隐私/感知策略 |

## 3. 目标架构（四层 + 两条数据流）

```
表现层      渲染进程：Live2D / 气泡 / 聊天 / 各面板
───────────
编排层      main 进程：事件总线 · 生命周期 · 窗口 · 装配(DI)
───────────
领域系统层   src/systems/*：情绪 · 好感 · 养成 · 日程 · 资讯 · 日记 · 主动
           （每个= 状态模型 + 领域行为 + 事件订阅 + 持久化读写）
───────────
基础设施层   persistence(JSON存储抽象) · memory(Graphiti/bge) · perception(感知源)
           · execute(pi 执行引擎) · llm(本地大脑/provider)
───────────
契约层      contracts/ipc + data-schemas（IPC 与数据模型都单源）
```

**两条数据流**（可维护性的核心）：
1. **感知→记忆**：感知源（时间/系统状态/屏幕/音频/资讯）只产出**事件**进统一 EventBus，不直接写任何地方。
2. **决策→行动**：系统订阅事件、读记忆/状态 → 决定「说话」还是「派活」→ 聊天输出 / pi 执行引擎。

任何新功能 = 注册一个事件源 或 订阅一段事件，不穿透 require；避免 `main.js` 再次成为上帝文件。

## 4. 可维护性原则（五个必守的坑）

1. **双大脑不抢写状态（铁律）**：**只有主进程是持久化唯一写方，大脑只能「建议」**。本地大脑建议情绪增量、pi 返回执行结果，均不直接写存储/记忆。状态如何落盘由领域系统在单点决定 → 可审计、可回滚、可单测。
2. **感知数据防黑洞（省存储 + 省云端 token）**：原始信号**永不落库**，只在「有意义变化/决策点」经最简过滤产出事件。录音=事件驱动录制，非无脑全录。
3. **pi 隔离到独立子进程/worker**：pi 依赖重，不随主进程常驻。主进程经「执行网关」请求任务。→ 启动快、崩溃隔离、Node 版本解耦、可 mock。
4. **权限与感知生命周期**：每种感知源（麦克风/屏幕/辅助功能）收敛为统一「感知配置 + 隐私策略」：权限状态检测、一键跳系统设置、可关、录音数据可遍历查看/一键删除。
5. **拒绝散装 JSON**：持久化抽象带 **schema 版本 + 迁移入口**，各系统走标准读写，杜绝格式漂移。

## 5. 领域系统设计模式（每个系统统一形态）

每个 `src/systems/*` 系统遵循：
```
state（状态模型，注入 system prompt）
  + domain（纯逻辑领域行为，可单测，不依赖 Electron/窗口）
  + events（订阅 EventBus 的事件，或向外派发事件）
  + persistence（经 storage 抽象读写，带 schema 版本）
```
领域逻辑**纯函数化**，与渲染/进程解耦 → 全部可单测。

## 6. 分阶段路线图

### P0 — 自主体地基（纯本地 · 零云端 · 可单测）
1. **事件总线 + JSON 存储抽象**（带 schema 版本/迁移）——一切的地基
2. **情绪 / 好感 / 养成** 状态系统 —— 参照遗留 `emotion-state.json` 复活并精简
3. **感知最小起点：系统状态 + 时间** —— 产出事件（深夜/连续使用→情绪/好感变化）
4. **对话注入** —— 状态摘要注入 system prompt（`{personality}` 扩展为 `{state}`）
- **P0 收尾（接云端）**：pi 执行引擎网关（独立进程 + 自定义领域工具 + 首个工具）

### P1 — 感知与时间（最实用）
- 日程记录、会议提醒、自动获取资讯（感知事件管道已就绪）

### P2 — 内部状态驱动
- 情绪/好感/养成状态影响决策与行动

### P3 — 自主 agent
- 主动会话（由状态/日程/情绪触发，非被动等输入）+ agent 执行

### P4 — 重感知 + 多角色
- 屏幕观测、录音生活日记、日记沉淀、多角色互动、群聊（依赖成熟 agent + 隐私框架）

## 7. 隐私策略（随感知模块落地）
- 录音**默认自动检测、可关**；事件驱动录制
- 每种感知源独立开关 + 权限状态检测 + 一键跳系统设置
- 感知数据可遍历查看、可一键删除；原始信号不落库
- 未来的屏幕观测同上处理

## 8. 里程碑交付约定
- 每阶段：实现 → 单测 → 真机验证 → commit → push（分支 `memory-poc` 或按需切分支）
- `npm run check` 保持全绿
